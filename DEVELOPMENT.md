# Developing Orcanva

Built with Next.js 16, React 19, Konva, Tailwind v4, shadcn/ui (Base UI), Drizzle, and Neon (Postgres, Auth, Realtime, and Object Storage).

## Setup

Requires Node 24 and pnpm.

```bash
pnpm install
```

### Environment

Create `.env.local` (gitignored) with your Neon project's values:

```bash
DATABASE_URL=postgresql://…            # neon connection-string
AWS_ACCESS_KEY_ID=…                    # neon credentials create --scope storage:read --scope storage:write
AWS_SECRET_ACCESS_KEY=…
AWS_ENDPOINT_URL_S3=https://<branch>.storage.<cell>.<region>.aws.neon.tech
AWS_REGION=eu-central-1
STORAGE_BUCKET=orcanva-assets
NEON_AUTH_BASE_URL=https://…/neondb/auth  # see "Accounts" below
NEON_AUTH_COOKIE_SECRET=…              # openssl rand -base64 32
NEON_REALTIME_URL=wss://…              # optional, see "Realtime" below
NEON_REALTIME_SECRET=…
RESEND_API_KEY=re_…                    # optional, sends share invites; see "Sharing" below
EMAIL_FROM="Orcanva <hello@example.com>"  # optional, at a domain verified in Resend
```

The storage endpoint and region come from `neon api /projects/<project>/branches/<branch>/storage`. Object Storage needs a project in `aws-us-east-1`, `aws-us-east-2`, `aws-eu-central-1`, or `aws-ap-southeast-1`.

### Database and storage

```bash
pnpm db:migrate                     # apply Drizzle migrations
pnpm storage:setup                  # allow browser uploads from any origin and smoke-test them
pnpm storage:setup https://my.app   # or restrict uploads to specific origins
```

Browsers upload straight to the private bucket with short-lived presigned URLs. If the bucket's CORS doesn't allow the page's origin, uploads fall back to going through the app (`PUT /api/assets/[id]/file`), so they work on any dev port. Images are read back through the same-origin `/api/storage/*` route, which keeps exports from being tainted.

### Accounts

Sign-in uses [Neon Auth](https://neon.com/docs/auth/overview) (Managed Better Auth), with Google and email + password. Users live in the branch's own `neon_auth` schema. Enable it on the branch, add the app's domain, and copy the base URL into `NEON_AUTH_BASE_URL`:

```bash
neon neon-auth enable --project-id <project> --branch main
neon neon-auth domain add https://my.app --project-id <project> --branch main
neon neon-auth status --project-id <project> --branch main   # shows base_url
```

`NEON_AUTH_COOKIE_SECRET` is your own random string (32+ characters) that signs the session cache cookie; keep it the same across deployments. Localhost is trusted by default. Google works out of the box on Neon's shared OAuth app, which shows Neon's name on the consent screen.

Designs guests make have no owner: they're public, nobody can rename them, and only an admin can delete them. Admins delete any public design from its card's menu, and an image on a public design for everyone from its properties (its file, every copy made from it or that it was made from, and the CDN's copy). Make an account one with its email, which must be verified (`--revoke` undoes it). It's Neon Auth's own admin role, so the account can use Neon Auth's admin API too:

```bash
pnpm make-admin you@example.com
```

Designs and uploads made before accounts existed have no owner either: they stay public until you hand them to an account (sign up with that email first):

```bash
pnpm claim-designs you@example.com
```

Before a real launch, from Neon's [production checklist](https://neon.com/docs/auth/production-checklist):

- Your own Google OAuth app, with redirect URI `{NEON_AUTH_BASE_URL}/callback/google`
- Your own SMTP provider (Neon's shared sender is rate-limited), then turn on email verification
- Turn off "Allow localhost" once development uses its own Neon branch

### Sharing

Invites and comment mentions go out through [Resend](https://resend.com). Without `RESEND_API_KEY`, sharing and mentions still work but no email is sent; the owner is told so for invites. `EMAIL_FROM` must be at a domain verified in Resend; it defaults to `Orcanva <orcanva@orcdev.com>`. Links in emails always point at production (`SITE_URL` in `lib/site.ts`) from production builds, and at the local server in dev (`lib/email/origin.ts`).

### Realtime

Live collaboration uses [Neon Realtime](https://neon.com/docs/realtime/overview) (beta, needs one of the regions above). Enable it on the branch and pull its two variables into `.env.local`:

```bash
npx neon@latest realtime enable --project-id <project>
npx neon@latest env pull --project-id <project> --service realtime --file .env.local
```

Without them the editor still works and saves, just without live updates.

Allowed origins are left at the default (any origin): the real gate is the sealed query, a short-lived token for one design's rows that this server only mints for people who may open the design, and re-checks on every renewal (about once a minute).

### Run

```bash
pnpm dev
```

The landing page is at `/`, the studio at `/studio`, and the editor at `/design/[id]`.

### AI tools

Background removal uses [BEN2](https://huggingface.co/onnx-community/BEN2-ONNX), whose weights are MIT-licensed so commercial use is fine, through [Transformers.js](https://huggingface.co/docs/transformers.js) on the visitor's GPU via WebGPU (recent Chrome, Edge, or Safari on a GPU with half-precision support). It runs in a Web Worker (`lib/ai/worker.ts`, which every AI tool shares: one model runs at a time, and the models are listed with their pinned revisions and licences in `lib/ai/models.ts`), not on the server: at its fixed 1024px input it needs several GB of memory, more than serverless functions get. The first removal downloads the model (~220 MB) into the browser's cache. After that, each image takes a few seconds. The cutout is uploaded as a new transparent PNG in your library and linked to its source, so repeating the removal is instant and **Restore original** can switch back.

Upscaling uses [Real-ESRGAN general v3](https://huggingface.co/vlad-grig/realesr-general-x4v3-onnx) (BSD-3-Clause, 2.4 MB in half precision), on WebGPU or, without it, on the CPU (much slower: the site has no cross-origin isolation, so WebAssembly gets one thread). The model always makes 4×; 2×, and sizes capped at 4096px or a 4K frame's worth of pixels (`lib/upscale/options.ts`), shrink each tile after it. Photos go through in 256px tiles that overlap by 16px and fade into each other (`lib/upscale/tiles.ts`), so memory stays flat and there are no seams. A photo with transparency has its clear pixels filled with the nearest edge colour first, so no dark fringe bleeds in, and its alpha goes through the model as a grey picture; it's saved as a PNG, and opaque results as JPEGs (`lib/upscale/encode.ts`). The result is a new asset linked to its source, like a cutout, so the same upscale again is instant.

The magic eraser uses [LaMa](https://github.com/advimman/lama) ([big-lama with int4/int8 weights](https://huggingface.co/othytenk/lama-int4-int8), Apache-2.0, 37 MB), on WebGPU or the CPU. It was picked over MI-GAN (MIT, 28 MB) by a bake-off on ten thumbnail-style photos: they tied on small things like a phone on a table or a watermark, and LaMa was clearly better on big holes (a person, big text), where MI-GAN left smears and invented shapes. Both models' weights were trained on Places2, whose terms allow non-commercial research and education; the weights' licence doesn't say how that carries over, and the `/magic-eraser` FAQ says so. LaMa takes a fixed 512 × 512, so only a square around the brush strokes goes to it (twice their size and at least 512px, `lib/magic-eraser/mask.ts`), fitted at its own shape and mirrored out to the square's edges; the fill comes back up to size and replaces only the painted pixels, grown by about two pixels at the model's scale so an object's soft edge goes too, while the photo keeps its own transparency. Each erase is kept as a patch of what that square looked like before and after (`lib/magic-eraser/erase.ts`), so undo and redo cost no model run, and `lib/magic-eraser/session.ts` orders strokes and erases for undo. In the editor the eraser works on the photo's own pixels in memory (`lib/editor/magic-eraser.ts`): strokes are kept in the photo's pixels, mapped from the element through its crop and flips (`lib/magic-eraser/geometry.ts`), so the mask lines up with the file however the image is cropped or turned, and the overlay (`components/editor/canvas/erase-overlay.tsx`) draws the work in progress filtered and flipped like the image itself. Nothing is saved until Done, which uploads the result once as an `erased` copy of the photo, waits until it's drawable so the original never flashes back, and swaps it in as one undo step. Erased copies are never looked up by their source (each depends on its mask), so a photo can have any number of them.

### AI agents

Two ways for an AI agent to make and edit designs. Both build elements from the same friendly specs (`lib/agent/specs.ts`: text, shapes, graphics and images with placement keywords, checked by the document schema), so a typo or a bad value comes back to the agent as an error and never reaches a design.

- **From a terminal agent** (Claude Code, Cursor, …): `pnpm mcp`, an MCP server that writes through the editor's save statement. See [mcp/README.md](mcp/README.md).
- **From an agent in the browser**: the editor offers its tools through [WebMCP](https://webmachinelearning.github.io/webmcp/) (`hooks/use-webmcp.ts`, `lib/webmcp/`) while a design is open, in browsers that have it (`document.modelContext`, or `navigator.modelContext` in older Chrome builds and polyfills); nothing happens in the others. The agent works on the design on screen as the person using it. Its edits go through the editor store, so they save, sync to everyone on the design, show a toast, and undo with Ctrl+Z. It gets what the browser has and the server doesn't: the real text measurements, a preview of the page as drawn, downloads, templates, and background removal and upscaling. Images come from URLs the browser can fetch. `get_design` is marked `untrustedContentHint`, since a design's text may be written by anyone it's shared with. In Chrome, WebMCP is in an origin trial: a deployment needs its own token, and for local testing it can be turned on in `chrome://flags`.

### Graphics

Icons are [Tabler Icons](https://tabler.io/icons) (MIT), emoji are [Microsoft Fluent Emoji](https://github.com/microsoft/fluentui-emoji) in their flat style (MIT), and the stickers are Orcanva's own, released as CC0: eight in `lib/graphics/builtin.ts` (so the Shapes tab needs no fetch) and the rest as SVGs in `assets/graphics/stickers/` with their names and keywords in `stickers.json`; their lettering is drawn as paths, and none copies a platform's logo. `pnpm graphics:build` (`scripts/build-graphics.ts`) turns them into a catalog in `public/graphics/<hash>/`: an `index.json` of every graphic's id, kind, name and keywords (the "For thumbnails" set from `lib/graphics/curated.ts` first within its kind), its art in shards of about 70 KB, and `NOTICES.txt` with both MIT licences. `lib/graphics/normalize.ts` makes each SVG drawable from flat paths: shapes become paths, transforms are applied, inherited and `currentColor` paint becomes palette entries, and coordinates are rounded to two decimals; gradients, masks, clip paths, filters, `<use>`, text and images are left out (about 80 emoji are, mostly for having more than 16 colours). The output is committed, so builds need no network. Tabler comes from `node_modules/@tabler/icons`; for the emoji only their names, keywords and upstream commit are kept (`assets/graphics/fluent-flat/metadata.json`), and their art carries over from the last catalog, so after changing the normalizer redraw them with `pnpm graphics:build --fluent <checkout of fluentui-emoji at that commit>` (a sparse checkout of `/LICENSE`, `assets/*/metadata.json` and the flat SVGs is enough).

### Templates

Starter templates are files in `lib/templates/data/`, one JSON design each, with their previews and any photos in `public/template-files/`. To make one, design it in the editor (with only your own photos or CC0 ones), then run `pnpm template:export <design id> --id <template id> --category <name> --tags a,b`. It reads the design from the database, re-encodes its photos as WebP at no more than twice the size they're shown at, names them by their SHA-256, saves a preview (the design's gallery thumbnail, or a sharper `--preview file.png`), rewrites `lib/templates/catalog.ts` and `documents.ts`, and runs the template checks; photos from your uploads need `--source` and `--license`. To change a template, `pnpm template:open <template id> <email>` makes a private design from it for that account; edit it, then export it again under the same id. Template ids are part of URLs, so never rename one. To suggest a template, make it a public design and link it in an issue.

## How it fits together

- Who may do what is one rule (`lib/auth/access.ts`): a design's owner manages it (rename, delete, visibility, sharing); people it's shared with may open and edit its canvas, public or private; anyone, guests included, may open and edit a public design's canvas; nobody else sees a private one, and every route answers 404 rather than revealing it exists. Guests can make public designs too, which have no owner (`ownerOfNewDesign` in `lib/auth/new-design.ts`, with a shared cap of 30 an hour, since guests can't be told apart). Admins are accounts whose Neon Auth role includes `admin` (`lib/auth/admin.ts`, read from `neon_auth.user` on each request rather than the session, so revoking it counts at once): they may delete any public design (`canDeleteDesign`) and delete an image on one for everyone (`canDeleteImageEverywhere`, `findImageFamily` in `lib/db/queries/assets.ts`). In SQL it's `visibleTo()` (`lib/db/queries/designs.ts`), which the save and presence statements use too. A share is a row in `design_shares` per email address. Email sign-ups aren't verified, so a matching address alone isn't enough: an account gets in when its email is verified (Google) or once it opens the emailed invite while signed in with that address, which ties the share to it. The link's token proves the inbox is theirs; only its SHA-256 is stored, and sending the invite again replaces it. `getViewer()` (`lib/auth/server.ts`) is how server code learns who is asking (Server Actions that need an account call `requireViewer()`), and every page, Route Handler, and Server Action checks for itself: `proxy.ts` only finishes Google sign-ins and keeps session cookies fresh, and only on the routes that read the session (its middleware sends any path it doesn't know to sign-in, so the landing's pages, crawl files and unknown URLs skip it). The save statement checks access on the design row it locks, so a design made private mid-edit takes no more writes from people who just lost access, and the live page query carries visibility so their editors stop at once.
- `lib/document/` is the versioned, zod-validated design document (elements, background, size) with migrations and factories.
- Starter templates are design documents kept in the repo as JSON (`lib/templates/data/`), not in the database, so they're reviewed like code and work on any deployment without seeding. `lib/templates/catalog.ts` lists them without their documents, small enough for the browser; the server loads a template's file only when it's used (`lib/templates/documents.ts`), and `instantiateTemplate` gives its elements fresh ids and groups (and scales it, should the size differ) before `createDesignFromTemplate` writes them as a new design's rows. `/new/<preset>?template=<id>` makes one too, after sign-up for guests. Most templates hold empty frames as photo slots; the images some do carry are files in `public/template-files/images/` named by their SHA-256, served straight from `public/` with immutable caching. Each has an `assets` row (`origin` `template`, no owner, a UUIDv5 of the hash as its id) written whenever its template is used, so its photos, a Remove background cutout of them and Restore original work as for uploads, while it stays out of every library (`pnpm claim-designs` only claims uploads).
- `lib/editor/` holds the per-editor zustand store, transactional undo history (a drag, slider scrub, or text edit is one step), and transform baking.
- The colour picker (`components/color-popover.tsx`) knows nothing about the editor: it takes a value, an `onChange` and rows of swatches. The editor's wrapper (`components/editor/panels/color-picker.tsx`) makes each open-to-close session one undo step, and fills the rows when it opens: the design's colours from `documentColors()` (`lib/document/palette.ts`, which lists every colour field per element type) and the recent ones this browser keeps in localStorage.
- `components/editor/canvas/` is the Konva workspace. Exports render an offscreen clone of the page at exact size after fonts and images load (`lib/export/`); downloading every page draws the others through the static page renderer, one at a time, and packs them with a small ZIP writer that stores the files as they are, since PNG, JPEG and WebP are compressed already (`lib/export/zip.ts`, loaded only when it's needed). A PDF is the same pictures as JPEGs at 2× (1× when 2× would be too many pixels), each embedded as it is to fill a page of the design's size in points (`lib/export/pdf.ts`, also loaded only when needed); a vector PDF would mean redoing curved text, effects, gradients and filters, and embedding fonts.
- The static page renderer (`components/editor/canvas/static-page.tsx`) draws a document read-only through the workspace's own nodes, with nothing listening, from a store of its own (`createStaticStore`), so photos, filters, effects and graphics look as they do in the editor. The version preview shows one fitted on screen (`StaticPageView`) and stays hidden until the render preparers (`lib/export/prepare.ts`: fonts, images, photo effects) say everything is drawn; `renderStaticPage` turns one into an image through `renderPage`. Off screen, `PageRenderHost` draws documents that aren't open (Magic Resize's previews and copies) one at a time with the editor's images.
- Magic Resize lays a document out again at another size in the browser (`magicResize` in `lib/editor/magic-resize.ts`, its thresholds in `MAGIC_RESIZE_RULES`), since measuring text needs the browser's fonts (`measureTextElement` in `lib/text/element-layout.ts`, the same layout the canvas draws). It splits the page into units: groups, things that overlap or nearly touch, the page's structure (anything covering 90% of an axis), and columns of stacked text with whatever sits between, each text carrying the small things beside it. Structure stretches with the page; every other unit scales by the smaller of the two ratios and stays by the edge or the centre it was nearest to (`rotatedBounds` in `lib/document/geometry.ts` gives every element's box), staying on the page if it was on it; text scales by the geometric mean of the ratios, wraps at a width that follows the page's, gets smaller rather than break a word, and a column too tall for the page shrinks as one. Resizing in place is one `change`, so one undo step and one outbox batch. A copy never touches the live queries: the browser lays it out and sends the whole design to `createResizedCopy` (`lib/actions/designs.ts`), which checks it with the changes route's own element checks (`lib/document/element-input.ts`) and writes the design and its rows in one batch. The previews and the copies' gallery pictures come from the static page renderer's offscreen mode (`PageRenderHost` and `usePageRenderer` in `static-page.tsx`), which mounts one page at a time from a queue (`lib/export/render-queue.ts`) in a hidden Stage and draws it once the render preparers are done.
- Each element is its own row in `design_elements` with a fractional-index `position` for z-order, so people editing different elements never overwrite each other (`lib/collab/positions.ts`). Each page is a row in `design_pages` too (its own `position` and background; every page has the design's size), and each element names its page, so adding or reordering pages never clashes either; a design's first page has the design's own id. The editor holds the whole design and shows one page as a document, so the canvas, panels and document ops work on a page as they always did. Edits become per-element and per-page change sets (`lib/collab/changeset.ts`); undo replays your own change sets on top of the current design, so it never reverts someone else's work, and never brings back an element or page someone else deleted.
- The outbox (`lib/collab/outbox.ts`) sends writes about every 100 ms to `POST /api/designs/[id]/changes`, which applies a batch in one statement and returns its transaction id. Creates upsert, updates only touch rows that still exist (a delete wins over a concurrent edit), and the last write to an element wins.
- Version history is snapshots in `design_versions`: a design's page settings and every element row as they were, kept whole as jsonb. The save statement takes them itself (`changesStatement` in `lib/db/queries/changes.ts`), so they cost no extra request and guests can't skip them: when the design has no version yet, its newest is over 10 minutes old, or someone else starts editing after a 30-second pause, the same statement copies the design as it was before that batch (`insertVersion` in `lib/db/queries/versions.ts`; every part of a statement reads the same snapshot), and nothing in that copy can fail the save. After the response, `after()` thins the history out (`lib/versions/retention.ts`): every version from the last day, then the newest of each hour for a week and of each day for a month, within 50 MB per design. Each version has a picture under `versions/<design id>/`: auto versions get a copy of the gallery preview in `after()` (it shows the state they hold, since editors draw it a few seconds after edits stop), named ones are drawn by the editor that saves them, and any still without one is drawn the first time it's previewed; pruning and deleting the design delete them. Assets an old version shows still count as in use (`isAssetReferenced`). A restore is one statement too (`restoreVersion`): it keeps the current state as a `restore` version (so it can be undone), upserts the version's element rows with their stored z-order keys and deletes every other row, so the rows end up exactly the version's, and raises `restore_seq`, which the live page query carries to every open editor: each clears its undo history (it was for a design that's gone) and says who restored. Version history is only for the owner and the people a design is shared with (`canManageHistory`, and `managesHistory()` in SQL); its routes answer 404 to everyone else, since old versions can hold what the owner removed on purpose.
- Comments are rows in `design_comments`, outside the elements and the version history, so restoring a version never touches them. A thread is its root comment, which holds the pin (page coordinates, and the page it's on: null is the first) and its replies point at it; author names and pictures are copied in, so reading them needs no join. A pin placed on an element keeps its spot in that element's own frame (`lib/comments/anchor.ts`): it moves, turns and scales with it, follows the element's Konva node mid-drag, and falls back to where it was put while the element is gone (deleted, or left out by a restore), following again if it comes back. Pins are an HTML layer over the canvas, the same size at any zoom; in comment mode a transparent layer takes clicks, so nothing on the canvas reacts, and finds the element under the click with Konva's hit test. Comments reach everyone on the design through their own live query; the window that posted or changed one shows it at once and keeps it on top of live results until they show it too (`withEchoes`). Posting is one statement (`postComment` in `lib/db/queries/comments.ts`) that checks the design is visible to the viewer, that a reply's thread is on it, and the limits: 30 comments per account every 10 minutes (then 429) and 1,000 per design. Changing one is a single statement too, with the rule in its WHERE (`lib/auth/access.ts` mirrors them for the UI): its author edits it, its author or the design's owner deletes it (a thread takes its replies with it), and the owner, the people it's shared with or whoever started a thread resolve or reopen it. Text is plain: React text nodes with `whitespace-pre-wrap`, never HTML, never auto-linked. Mentions are `<@user id>` tokens in the text (`lib/comments/body.ts`) with the names they stand for copied into the comment's `mentions`, so everyone reads them as names without a lookup. Only the owner and the people a design is shared with can mention, or be mentioned (`isMentionable`): the composer's list comes from `GET /api/designs/[id]/people` (names and pictures, never emails), and the statement that posts a comment checks each token again and writes a `comment_mentions` row per person. After the response, `notifyMentions` (`lib/comments/notify.ts`, in `after()`) emails them a link to `/design/<id>?comment=<thread>`, which opens the design on that thread: not the author, nobody whose editor is on the design (seen in the last 15 seconds), at most one email per person and design every 15 minutes and 20 per person an hour, and 30 an hour caused by one author. There's no reply-to, so authors' addresses stay private. Mail never goes to reserved domains such as example.com (`lib/email/reserved.ts`), so test accounts cause no bounces.
- Live updates come from five [Neon Realtime](https://neon.com/docs/realtime/overview) live queries per design (the design row, its pages, element rows, presence rows, comments), sealed on the server (`lib/realtime/server.ts`) and renewed through `POST /api/designs/[id]/live`. They're sealed together, so they expire together, and one request a minute renews them all (`lib/collab/renewals.ts`: renewals asked for within 250 ms share a request, which always asks for every query, and a query asking a little later takes the one kept for it); the route still renews one query at a time for tabs opened before that, and gives tabs from before pages (whose renewals carry no `v`) only the first page's elements, the one page they can show. Their saves still work: elements they add land on the first page, and the background they set is the first page's (`changesPayload` in `lib/document/changes-payload.ts`). The editor shows the server's rows with its own unconfirmed writes on top (`lib/collab/sync-state.ts`) and keeps each write there until its transaction comes back on the live query, so a lagging result after a reconnect can't hide your own edits. If the connection drops for good, a watchdog starts a fresh session.
- A page strip (`components/editor/page-strip.tsx`) lists the pages, each drawn small by the static page renderer's offscreen mode a moment after it changes (`hooks/use-page-thumbnails.ts`), and reorders them with `@dnd-kit/sortable` as Layers does. Page actions (`lib/editor/page-actions.ts`) are change sets like any edit: adding or duplicating a page is a page create (plus its copied elements, with fresh ids and the same z-order keys), deleting one writes out the delete of each of its elements so one undo brings everything back, moving one rewrites only the keys that must change, and a resize or page crop runs the same change on every page as one step (`changeAllPages`). The save statement stores pages before the elements that land on them, so undoing a page delete is one statement, and a write to a page someone else deleted is dropped as an edit to a deleted element is. A design with more than one page is stored with document version 2: tabs from before pages see that on the live design row and stop (below) rather than save only the first page, while a design that never had a second page stays at version 1, which older code still opens.
- Editors stay open across deploys, so a tab can meet what newer code wrote. It keeps the fields it doesn't know on the elements it edits, and leaves out whole elements it can't read (a newer element type) rather than failing: they stay off its canvas and out of a paste, and older server code still opens the design without them (`migrateDocument`). While a design has such elements, the editor says that a reload shows them, and leaves the gallery preview to a tab that can draw them. A tab that's too old to go on stops: when the design's `version` (on the live page query) passes the tab's `DOCUMENT_VERSION`, or a Server Action it calls is gone (their ids change with each deploy, and Next says "Failed to find Server Action"), it sends the edits it has, refuses new ones, leaves presence, and asks for a reload (`components/editor/outdated-dialog.tsx`).
- Cursors, selections, in-progress drags and the page each person is on are rows in `design_presence`, written about 10 times a second while you move (`PUT /api/designs/[id]/presence`, with a heartbeat every 5 s) and read by the presence live query. Positions are in page coordinates, so they line up at any zoom. You only see the cursors, selections and drags of people on your page (`peersOnPage` in `lib/collab/presence.ts`; a row without a page, from a tab older than pages, is on the first), and the avatars say which page everyone else is on.
- Graphics (icons, emoji and stickers) carry their own art: a viewBox, a palette, and layers of SVG path data whose fill and stroke are palette indexes, so a design never depends on the catalog it came from (copying one into another design, or a later catalog renaming it, changes nothing). `components/editor/canvas/graphic-node.tsx` draws them on one Konva shape with `lib/graphics/draw.ts`, a cached `Path2D` per layer mapped from the viewBox onto the box, so they're vectors at any zoom and in 2× exports; the shape has a fill and a stroke it never paints, so Konva composites it through a buffer while it's see-through and the layers fade as one picture. Clicks hit the whole box. The Graphics tab (`components/editor/panels/graphics-panel.tsx`) fetches the catalog the first time it opens (`lib/graphics/catalog.ts`; never imported, so it's in no bundle): `index.json`, searched in memory by `lib/graphics/search.ts` (exact name, then the name or a word in it starting with the query, then every query word starting a name word or keyword, then anywhere; stickers before emoji before icons), and only the shards holding the results on screen. The files sit under `/graphics/<hash>/`, served with `Cache-Control: immutable` (`next.config.ts`) and outside the proxy. Dragging carries the graphic's own JSON, so the drop needs nothing else.
- Image filters are data on the element (`filter`: a preset id, its intensity, and the slider values), never baked into the file, so they sync, undo, and copy like any other property. A WebGL2 shader (`lib/image-filters/`) draws the photo through them into a canvas that Konva shows instead of the photo; exports share that canvas. Filtered pixels are kept at up to twice the element's page size, which covers retina screens and the 2× export. Browsers without WebGL2 show images unfiltered.
- Photo effects are element data too (`outline`, `glow`, `shadow`: colours and sizes in page px, scaled whenever the photo is, by a corner resize, a page resize or Fill page; a side-handle crop leaves them alone). `lib/photo-effects/` draws them on the filters' WebGL2 context: what the photo shows (its cut-out's transparency through crop, flips, rounded corners or a frame's shape) becomes a mask, a jump flood finds every pixel's nearest point of it for an exact, round outline, and the glow and the shadow blur the photo and outline together. The bitmaps (twice the photo's page size, so retina screens and 2× downloads stay sharp) hang on a Konva shape the size of the photo's box, drawn behind it, so handles, snapping and clicks stay on the box, dragging redraws no bitmap, and exports share them. They're redrawn at most once a frame and only when something they follow changes; a colour, opacity, glow or blur change reuses the photo's distance field, and exports and thumbnails wait for pending redraws. The shadow's offset is applied as it's drawn, turned back by the photo's rotation so it falls the same way on the page, as text shadows do. Without WebGL2 the same effects are drawn on 2D canvases instead (an exact distance transform on the CPU, and canvas shadows for the blurs): slower, but alike.
- The landing page (`app/(marketing)/`) is prerendered and reads no session, so it's the same for everyone; signing in from it lands in the studio (`STUDIO_PATH` in `lib/routes.ts`). The hero painting and the product screenshot each come in a light and a dark version, picked by the theme class (`components/landing/themed-image.tsx`); the hidden version is fetched once the page is idle, so switching themes doesn't wait on the network. - Gallery thumbnails upload to `PUT /api/designs/[id]/thumbnail`, rendered by whichever window made the change. - The YouTube preview (`components/youtube-preview/`) is plain DOM, with no Konva, so a landing page can use it too. In the editor, `hooks/use-design-preview.ts` draws the design the way Download does, as one small JPEG that every slot shows, and draws it again 300 ms after the last change, a collaborator's included. `components/editor/youtube-preview-context.tsx` shares that one render between the dialog, the corner preview and the badge guide (`youtube-preview-overlays.tsx`), and only makes it while one of them shows; the guide is the mock's own badge, scaled from the smallest thumbnail (Up next) to the page's 16:9 frame on screen. The mock's sizes are constants in `lib/youtube-preview/layout.ts`, dated, since the real site's change, and a frame wider than the window is scaled down with CSS `zoom`; the title, channel, picture (an 88px JPEG cropped in the browser) and length are kept in localStorage (`lib/youtube-preview/details.ts`), never on the server; compares are blob URLs of local files or other designs' gallery previews (`listCompareDesigns` in `lib/actions/preview.ts`, the account's own 30 newest), so they can lag a few seconds behind an edit, and `arrangeFeed` spreads them through the made-up videos; its colours are plain greys in `lib/youtube-preview/theme.ts`, and its top bar has a blank block where a logo would be: no logo, wordmark or play icon, and a note says it isn't affiliated with YouTube.
- Files are served through `/api/storage/*` with immutable caching and random keys, so a storage URL works as a capability: whoever has one can load that image, the way a design's collaborators need to. Vercel's CDN keeps them for a year, tagged with their key (`Vercel-Cache-Tag`), so deleting a design or an image for good also drops the CDN's copies (`purgeStorageCache` in `lib/storage/cdn.ts`); browsers that already loaded one keep it. Thumbnails get a fresh random key on every save, and another when a design goes private.
- Settings (`/settings`) changes the account's name and avatar through Server Actions in `lib/actions/account.ts`. The browser crops an avatar to a 256px JPEG (`lib/upload/prepare-avatar.ts`), stored under `avatars/<user id>/` with a new key each time, and the replaced one is deleted. Neon Auth caches the session in a cookie for five minutes, so each change drops that copy (`forgetCachedSession`) and the new name shows at once.
- A brand kit is rows in `brand_kit_items`, one per colour, font or logo, unique per account, kind and value, so two tabs adding at once can't overwrite each other. Colours are stored as lowercase hex, fonts as catalog ids and logos as the id of one of the account's own ready uploads (deleting the upload takes the logo with it). The Server Actions in `lib/actions/brand-kit.ts` add with one statement that only inserts while the account is under its limit for that kind (the neon-http driver has no interactive transactions) and return the whole kit, so a change shows at once and is then corrected from what's stored (`changeBrandKit`, used by Settings and the editor alike). The editor loads the kit with the design and keeps it in its store; other tabs see a change when they next open a design. Guests have no kit and see none of it.
- Uploads belong to the account that made them and form its library, shared by all of its designs; a design also loads whatever its images show from other people's uploads. Uploading needs edit access to the design it's made from. Files are deduplicated by SHA-256 within one account only, since the hash comes from the browser. Guests' uploads have no owner and stay out of every library.
